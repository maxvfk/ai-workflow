# Реализация F-01 в пилоте: режим «только control plane»

Как пробел F-01 (и вместе с ним F-02) закрыт в проекте `SP-LAB-GRANT` поверх стандарта 0.8.6. Описание фактической реализации — кандидат в текст G2, а не готовая спецификация.

Проверено одной реальной задачей: чат подготовил разбор по теме проекта, положил отчёт в `_ai/inbox/`, агент с полным доступом его разобрал и обновил память проекта. Замечание по итогам первой проверки — F-15 отчёта, учтено в шаблоне.

## Задача

У пользователя есть резервный агент — чат с коннекторами GitHub и Google Drive, который включается, когда исчерпаны лимиты основного. Он **видит control plane и внешнее хранилище, но не видит artifact root**. G2 0.8.6 описывает только зеркальный случай (artifact-only).

Требования, которые пользователь сформулировал:

- задачи ручные и под прямым контролем: разобраться в вопросе, подготовить файлы;
- результат должен попадать в проект так, чтобы агент с полным доступом мог его разобрать позже;
- artifact root на другом облаке, места там мало — зеркалить его нельзя;
- итоговые артефакты не должны молча становиться каноническими.

## Решение

```text
чат ── читает ──► GitHub: AGENTS.md, STATE, TASKS, PROJECT, SOURCES, _ai/snapshots/
   │
   ├── создаёт файлы ──► внешнее хранилище: <Проект>/Входящие/   (не канонические)
   └── пишет отчёт ────► GitHub: _ai/inbox/ГГГГ-ММ-ДД-<тема>.md  (только новые файлы)
                                  │
     агент с полным доступом ◄────┘  сверка → project memory → архив отчёта
```

Пять элементов:

1. **Раздел runtime в каноническом `AGENTS.md`** — что можно, что нельзя, как сверяется.
2. **Входящая зона** во внешнем хранилище — единственное место, куда чат кладёт файлы.
3. **`_ai/inbox/`** с шаблоном отчёта — один новый файл на задачу.
4. **`_ai/snapshots/`** — снимки ключевых текстов artifact root только для чтения (это и есть закрытие F-02).
5. **Тонкий адаптер продукта** — текст для инструкций чата, который не дублирует правила.

## 1. Раздел в каноническом `AGENTS.md`

Установленный в пилоте текст, с заменой конкретных имён на плейсхолдеры:

> **Режим «облачный чат» (control plane + внешнее хранилище, без artifact root)**
>
> Для агента, которому доступны только этот репозиторий и `<хранилище>`, без доступа к синхронизированной папке проекта. Работа ведётся вручную под прямым контролем пользователя; решение — `<D-###>`.
>
> Разрешено:
> - читать project memory и другие файлы этого репозитория; ключевые документы artifact root — по снимкам только для чтения в `_ai/snapshots/`; прочие файлы artifact root пользователь прикладывает к чату сам;
> - создавать файлы **только** в папке `<хранилище>/<Проект>/Входящие` (идентификатор папки указан здесь же);
> - по итогам задачи создать **один новый** файл отчёта в `_ai/inbox/` по шаблону `_ai/inbox/README.md`.
>
> Запрещено:
> - изменять `STATE.md`, `TASKS.md`, `SOURCES.md`, `PROJECT.md`, `ASSUMPTIONS.md`, `AGENTS.md`, снимки, решения, планы и чужие отчёты — предложения по их обновлению пишутся в отчёт;
> - выдавать снимок за текущее состояние оригинала: снимок датирован и может отставать;
> - утверждать что-либо о содержимом artifact root, которое агент не видел;
> - считать файлы во входящей зоне каноническими артефактами проекта;
> - записывать в отчёт или во внешнее хранилище секреты и учётные данные.
>
> Сверка (агент с полным доступом, по запросу пользователя или при восстановлении контекста, если в `_ai/inbox/` есть неразобранные отчёты):
> 1. прочитать отчёты и указанные в них файлы; отчёт — свидетельство, не источник истины;
> 2. внести существенные выводы в `STATE.md` / `TASKS.md` / `SOURCES.md` / решения;
> 3. по каждому файлу во входящей зоне согласовать с пользователем: перенести в artifact root и зарегистрировать; или оставить во внешнем хранилище и зарегистрировать как внешний источник с идентификатором; или не сохранять;
> 4. перенести разобранный отчёт в `_ai/archive/inbox/`;
> 5. файлы во внешнем хранилище не удалять — это делает пользователь.

Дополнительно в `AGENTS.md` добавлена строка в блок `Infrastructure` (что режим установлен, где входящая зона) и пункт в порядок запуска: агент с полным доступом проверяет, есть ли неразобранные отчёты в `_ai/inbox/`, и сообщает о них пользователю.

## 2. Входящая зона

Обычная папка во внешнем хранилище, указанная в `AGENTS.md` по имени и идентификатору. Допустимы нативные документы хранилища (в пилоте — Google Docs и Sheets). Содержимое не канонично: до сверки это черновики.

Удаление оставлено пользователю осознанно: место в хранилище ограничено, а решение «это больше не нужно» — не агентское.

## 3. `_ai/inbox/` и шаблон отчёта

Правило одно: **один новый файл на задачу, существующие не редактируются**. Это снимает конкуренцию за файл и делает историю линейной.

Шаблон (после правки по итогам первой проверки, F-15):

```markdown
# <краткое название задачи>

Date: YYYY-MM-DD
Agent: <продукт / модель>
Mode: облачный чат (control plane + внешнее хранилище)

## Задача
## Использованные данные
- GitHub: <файлы репозитория>
- Приложено пользователем: <файлы из artifact root, если были>
- Внешние источники:

## Созданные файлы во входящей зоне
- <название> — <тип> — <ссылка или идентификатор> — <что это>

## Результаты и выводы
- <указывать статус: расчёт / оценка / не проверено / из источника>

## Расхождения с данными проекта
- <предпосылки задачи, не совпадающие с прочитанной памятью проекта; «нет», если проверено>

## Предлагаемые обновления project memory
- STATE / TASKS / SOURCES / решения

## Открытые вопросы
```

Два пункта появились из опыта, а не из теории:

- **«Расхождения с данными проекта»** — в первой же задаче чат опирался на предпосылки из беседы, которые расходились с зафиксированными в проекте, и сам этого не заметил (F-15).
- **Требование писать формулы простым текстом с Unicode**, а не LaTeX с обратными слэшами: они искажаются при записи в репозиторий (F-14).

## 4. `_ai/snapshots/` — закрытие F-02

Снимки ключевых текстов artifact root, только для чтения. У каждого файла шапка:

```text
> Снимок только для чтения — не редактировать. Оригинал: artifact root, `<путь>` (<редакция/дата>).
> Снят <дата> агентом с полным доступом; sha256 оригинала на момент снятия: `<хэш>`.
> Каноническая версия — в синхронизированной папке проекта. Предложения по правкам — в отчёт `_ai/inbox/`.
> Рисунки и относительные ссылки из снимка не открываются.
```

`_ai/snapshots/README.md` — индекс: таблица «снимок → что это → sha256 оригинала», плюс правила: снимки не редактируются; обновляет только агент с полным доступом (при сверке сравнивает sha256 и заменяет устаревшее целиком); состав снимков определяет пользователь; в `SOURCES.md` снимки не регистрируются.

Практическое дополнение: в индекс полезно класть короткую сводку ключевых параметров проекта со ссылками на разделы снимков. Чат так быстрее ориентируется и реже строит выводы на устаревших числах.

Контрольная сумма здесь не противоречит запрету G2 §11 на изменяемые хэши: снимок неизменяем по определению, а хэш относится к оригиналу на момент снятия и служит ровно для обнаружения расхождения.

## 5. Адаптер продукта

Для агентов, которые не находят `AGENTS.md` сами. Хранится в `_ai/adapters/<ПРОДУКТ>.md`, содержит только маршрут, без дублирования правил:

```text
Проект <Название> (Project ID: <ID>). Канонические инструкции и память проекта — в репозитории <owner/repo>.

Перед работой:
1. Прочитай AGENTS.md из репозитория (ветка main), раздел «Режим „облачный чат“», и следуй ему.
2. Прочитай STATE.md и TASKS.md; остальное — по необходимости.
3. Рабочая папка проекта тебе недоступна. Ключевые документы есть в _ai/snapshots/ — это датированные копии только для чтения.
   Если нужен другой файл — попроси приложить его.
4. Создавай файлы только во входящей папке <хранилище>/<Проект>/Входящие.
5. В конце задачи создай один новый отчёт в _ai/inbox/ по шаблону _ai/inbox/README.md. Другие файлы репозитория не изменяй.

Если репозиторий или хранилище недоступны — скажи об этом и не продолжай так, будто контекст проекта восстановлен.
```

Для рабочего пространства из нескольких проектов такой адаптер один, со списком проектов; где ему лежать — открытый вопрос F-13.

## Что показала проверка

Первая реальная задача прошла по правилам полностью: чат изменил ровно один файл (новый отчёт в `_ai/inbox/`), ничего больше не тронул, отчёт соответствовал шаблону, статусы величин проставлены, предложения по памяти проекта отделены от выводов. Арифметику отчёта агент с полным доступом пересчитал независимо — сошлась. Единственное замечание — F-15, закрыто правкой шаблона.

## Открытые места

- **Размер и состав снимков** определяет пользователь вручную. Автоматического правила «что достойно снимка» нет и, возможно, не нужно.
- **Устаревание снимков** обнаруживается только при сверке. Чат может работать с датированной копией, не зная, что оригинал изменился; поэтому в правилах стоит запрет выдавать снимок за текущее состояние.
- **Адаптер уровня рабочего пространства** пока лежит в пилотном проекте (F-13).
- Режим не проверялся в сценариях, где чат должен работать с большими данными artifact root: он для этого и не предназначен.
