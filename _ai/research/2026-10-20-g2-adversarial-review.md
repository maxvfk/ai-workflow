## Находки

### 1. Локальная проверка служит основанием межмашинного завершения

**Codex:** критично · **Claude:** согласен
**Разделы:** G2 §§12–14, 18–19

**Сценарий.** Агент на машине A проверяет сохранённый файл и записывает `done` в GitHub. Клиент синхронизации задержал загрузку или пропустил изменение. Машина B получает новый `STATE.md`, но работает со старым артефактом, без конфликтных копий. Все предусмотренные локальные проверки проходят. Codex указывает, что потеря файловых уведомлений возможна на уровне Windows ([ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)).

**Предложение.** Различать «локально проверено» и «готово к продолжению на другой машине». Для существенных результатов задавать идентификатор версии и проверяемый состав публикации; принимающая машина подтверждает получение этой версии. Без способа проверить доставку сохранять явный статус `sync pending` или `sync unknown`.

**Проверка.** Подтверждено эмпирически — см. раздел «Случай Яндекс.Диска 2026-10-06».

**Решение:** `open`

### 2. Повторная проверка цели без baseline не ловит параллельную правку

**Codex:** критично · **Claude:** согласен
**Разделы:** G2 §§17–19; COMMON §14

**Сценарий.** Агент копирует XLSX во временную папку. Пока он работает, пользователь сохраняет новую версию оригинала. Перед публикацией оригинал существует, открывается и не имеет конфликтной копии — агент заменяет его своим результатом. Стандарт требует «re-check», но не определяет, с какой исходной версией сравнивать. Изменение с другой машины к этому моменту может ещё не прийти.

**Предложение.** При замене существующего файла сохранять временный baseline исходного содержимого (в рабочей области, а не в `SOURCES.md`) и сверять с ним перед заменой. Для нескольких машин дополнительно нужен явный порядок передачи права записи. Локальное сравнение не выдавать за распределённую блокировку.

**Проверка.** Оценено.

**Решение:** `open`

### 3. Публикация набора зависимых файлов неатомарна

**Codex:** критично · **Claude:** согласен; для CAD-проектов это ключевая находка
**Разделы:** G2 §§13, 17–18

**Сценарий.** Агент публикует изменённую CAD-сборку и несколько деталей. На другой машине новая сборка появляется раньше деталей. Все зависимости существуют и открываются, но часть относится к предыдущей версии; проверка отсутствующих ссылок ничего не обнаружит. Даже полностью корректная публикация на A не гарантирует корректного рабочего набора на B.

**Предложение.** Для зависимых наборов определить единицу публикации: отдельный каталог версии либо пакет с manifest состава и fingerprints. Потребитель принимает версию только после проверки всех компонентов; одного появления manifest или файла готовности недостаточно.

**Комментарий Claude.** Для SolidWorks естественная реализация — публикация в новый каталог версии (например, через Pack and Go) с последующим переключением ссылки в `SOURCES.md`, а не перезапись сборки на месте.

**Проверка.** Оценено.

**Решение:** `open`

### 4. Нет восстановления после частичной публикации между planes

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §18; COMMON §13

**Сценарий.** Артефакт уже заменён, но обновление GitHub отклонено или процесс агента завершился. Правило запрещает объявлять работу законченной, однако следующий агент не получает обязательного признака незавершённой операции. Он может повторить преобразование или продолжить по старым предпосылкам.

**Предложение.** Перед существенной публикацией фиксировать в задаче короткую pending-запись: операция, затронутые пути, ожидаемая версия. Определить восстановление после сбоя и обязательную проверку таких записей при продолжении работы. Заранее решать, каким способом будет опубликовано связанное изменение project memory.

**Комментарий Claude.** `COMMON.md` (строка 321) требует оставлять недоступную запись явной pending work. Но это покрывает случай, когда агент жив и сам сообщает о незавершённости. Обрыв посреди транзакции, когда сообщить уже некому, не покрыт — для него нужна запись, сделанная до публикации. В G1 подробная дисциплина есть (§17), в G2 специфичного раздела нет.

**Проверка.** Подтверждено (`COMMON.md`, строка 321; отсутствие pending-правил в G2).

**Решение:** `open`

### 5. Codex не находит корневой `AGENTS.md` из вложенной папки

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §§6–7, 23; COMMON §16

**Сценарий.** Пользователь запускает Codex CLI из `<artifact-root>\CAD\Coil`. Синхронизируемая папка G2 по замыслу не является Git-репозиторием, а отдельный корень проекта не настроен. Codex при отсутствии project root проверяет только текущий каталог. Корневой bootstrap `AGENTS.md` не читается: агент не узнаёт ни GitHub-репозиторий, ни правила G2.

**Предложение.** Определить поддерживаемый запуск из artifact root (например, `codex --cd <artifact-root>`) или явную настройку обнаружения корня. Cold-start проверять отдельно и для запуска из вложенного каталога. Обещание автоматического обнаружения ограничить фактически проверенными условиями.

**Проверка.** Подтверждено [документацией Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md): «If Codex cannot find a project root, it only checks the current directory»; project root — как правило, корень Git. Claude Code, напротив, читает `AGENTS.md` в рабочем каталоге и во всех каталогах выше, поэтому из вложенной папки корневой файл найдёт. Поведение двух агентов асимметрично.

**Связь.** Зеркало issue #3 со стороны Codex.

**Решение:** `open`

### 6. Нет исполнимого launch contract для двух корней

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §§4, 15; Registry §§3, 10–12

**Сценарий.** Агент запущен в artifact root, а внешний checkout control-репозитория не входит в разрешённые для записи пути. Для реестра обратная проблема: запуск в `PROJECTS/` не загружает runtime из отдельного репозитория. Простое добавление каталога не равнозначно загрузке инструкций.

**Предложение.** Дать конкретный launch contract для обоих CLI: стартовый каталог, явная загрузка authoritative runtime, подключение artifact root, соответствие путей в рамках сессии, необходимые права. Проверять эти возможности до существенной работы. Для реестра это особенно важно, потому что локальный bootstrap там намеренно запрещён.

**Проверка.** Подтверждено документацией Claude Code ([memory](https://code.claude.com/docs/en/memory#load-from-additional-directories)): `CLAUDE.md` каталогов, добавленных через `--add-dir`, загружается только при `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`, а их `AGENTS.md` не загружается вовсе.

**Связь.** Развивает issue #5. Предложенное там чтение и запись project memory через GitHub Contents API снимает часть проблемы: control-репозиторий тогда не нужно подключать как каталог.

**Решение:** `open`

### 7. Offline fallback ссылается на недоступные ему правила

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §7 (локальный шаблон, Artifact-only fallback), §22; COMMON §0

**Сценарий.** GitHub недоступен. Локальный bootstrap требует оставить отчёт «as defined by the G2 runtime», но определение места и формата отчёта находится в недоступном runtime. Там же — подробные sync-sanity rules, а ограничения конкретных источников могут быть только в `SOURCES.md`. Агент не может установить, достаточно ли локального контекста для безопасной работы.

**Предложение.** Материализовать локально минимальный самодостаточный offline contract: допустимые операции, проверки синхронизации, условия остановки, формат handoff. Для offline-задачи требовать явный scope и сведения о защищённых входах. При неизвестных ограничениях разрешать только подготовку отдельного результата без замены исходника.

**Проверка.** Подтверждено: G2, строка 206 — «leave a `_LOCAL_AGENT_REPORT.md` handoff near the changed files as defined by the G2 runtime».

**Решение:** `open`

### 8. Мелкие правки обходят канонический runtime

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §7 (шаблон, «Before substantial work»), §18; COMMON §3

**Сценарий.** Агент получает просьбу исправить одну ячейку и трактует её как bounded small edit. Локальный bootstrap требует читать GitHub только перед substantial work — агент пропускает канонический `AGENTS.md` и не узнаёт действующих ограничений. Другой агент применит COMMON и сначала загрузит runtime. У обеих интерпретаций есть текстовое основание.

**Предложение.** Отделить обязательное чтение канонического runtime от масштаба последующих проверок: при доступном GitHub runtime читается перед любой работой, а облегчаются только дополнительные чтения и publication workflow. Исключение — только artifact-only fallback.

**Проверка.** Подтверждено: G2, строка 190 — «Before substantial work:».

**Связь.** Уточняет issue #11, п. 4 («лёгкий путь»): облегчать можно проверки, но не вход в runtime.

**Решение:** `open`

### 9. Нет процедуры для плейсхолдеров и состояния синхронизации

**Codex:** существенно · **Claude:** согласен
**Разделы:** G2 §§12–14

**Сценарий.** Shell видит путь и размер облачного плейсхолдера OneDrive, но содержимое не загружено, и агент считает файл доступным. Другой агент видит статус online-only и объявляет provenance conflict, хотя достаточно скачать файл. В Яндекс.Диске отключённая синхронизация папки убирает файлы с диска — отсутствие нельзя автоматически трактовать как удаление. Источники: [OneDrive](https://support.microsoft.com/en-us/onedrive/what-do-the-onedrive-icons-mean), [Яндекс.Диск](https://yandex.com/support/yandex-360/customers/disk/desktop/windows/en/sync-folders).

**Предложение.** Различать доступность содержимого, состояние транспорта и конфликт версий. Определить ограниченную процедуру: загрузка нужного рабочего набора, проверка чтением, повторная проверка после загрузки. Если статус провайдера агенту недоступен, результатом проверки должно быть «неизвестно» с указанием способа получить подтверждение.

**Проверка.** Подтверждено эмпирически: в случае 2026-10-06 файл находился в состоянии `CF_IN_SYNC_STATE_IN_SYNC` при устаревшем содержимом.

**Решение:** `open`

### 10. Реестр подхватывает инструкции дочерних проектов

**Codex:** существенно · **Claude:** согласен
**Разделы:** Registry §§3, 5–6; COMMON §16

**Сценарий.** Агент реестра работает из `PROJECTS/` и читает manifest или `STATE.md` дочернего проекта. Claude Code подгружает `CLAUDE.md` подкаталога, когда читает файлы в нём, а вместе с ним и `@AGENTS.md`. Дочерний runtime требует восстановить другой проект и выполнять его стартовые правила. Запрет parent runtime устраняет одно направление наследования, но не обратное.

**Предложение.** Явно объявить дочерние instruction-файлы исследуемыми данными, а не активным runtime реестра. Добавить способ изоляции на уровне сессии и проверить поведение реальным cold-start; одной декларации read-only недостаточно.

**Комментарий Claude.** Для Claude Code конкретный механизм уже есть — настройка `claudeMdExcludes`, она действует и на `AGENTS.md`. Аналог для Codex не установлен.

**Проверка.** Механизм ленивой загрузки подтверждён [документацией Claude Code](https://code.claude.com/docs/en/memory#how-claudemd-files-load).

**Решение:** `open`

### 11. Общий append-отчёт конфликтует, обязательность размыта

**Codex:** существенно · **Claude:** скорее мелко
**Разделы:** G2 §7 (Local handoff report), §§18, 22–23

**Сценарий.** Два offline-агента меняют разные артефакты в одном каталоге и дописывают один `_LOCAL_AGENT_REPORT.md`. Артефакты не конфликтуют, а отчёт конфликтует или теряет запись. После reconciliation нет правила, какие записи уже обработаны, и следующие агенты повторно разбирают накопленный журнал.

**Предложение.** Установить одно условие обязательности. Для независимых задач — отдельные отчёты с уникальными task/run ID и явными путями относительно artifact root. Определить обработку и архивирование после reconciliation. Для малых изменений без значимого handoff разрешить отчёт в ответе.

**Проверка.** Расхождение подтверждено: G2, строка 280 — отчёт «recommended», строка 592 — «leave a scoped `_LOCAL_AGENT_REPORT.md` after delegated changes».

**Решение:** `open`

### 12. Не определён вход bounded reconciliation

**Codex:** существенно · **Claude:** согласен
**Разделы:** COMMON §3 (Manual/external/delegated changes); G2 §§7, 20; Registry §5

**Сценарий.** Пользователь меняет несколько файлов в разных ветках дерева без отчётов, затем просит «обновить состояние». Агенту предписан change-focused проход, но нет ни baseline, ни списка изменённых областей. Два агента проверят разные подмножества, и оба объявят состояние актуальным. Для реестра проект, отсутствующий локально из-за выборочной синхронизации, дополнительно выглядит как устаревшая запись каталога.

**Предложение.** Определить вход reconciliation: известный scope изменений, handoff или явно согласованный охват. При неизвестном scope фиксировать покрытие проверки и оставшиеся неизвестными области. Отсутствие локального пути без подтверждения полноты синхронизации не должно служить основанием для удаления записи реестра.

**Проверка.** Оценено.

**Решение:** `open`

## Случай Яндекс.Диска 2026-10-06
